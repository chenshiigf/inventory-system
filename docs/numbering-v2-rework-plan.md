# 商品编号 V2 重构基线（2026-10-28）

## 目标与严格范围

- 历史所有商品（含停用、未分类）按数据库 `products.id ASC` 排名分配 `250001` 起的连续编号。以**换号当时的冻结商品数**为准，不硬编码 2523。不能把商品主键直接当流水号。
- 之后新增商品按北京时间建档年月分配 `YYMM + 至少两位流水`，例如 2026 年 10 月 `261001`；不随分类、库存、包装、仓库改变，不重复，不因事务回滚浪费号码；API 创建和正式 Excel 导入调用同一创建服务。
- `original_product_code` 是原供应商货号，不允许填入旧自家货号。保存独立的 `old_internal_code -> new_code -> product_id` 不可变映射（完整对应关系随备份保留，是否加持久表由实现方案论证）。旧号搜索的行为需明确测试，避免客户历史单据无法追溯。
- 只变更商品自家编号以及必要的发号记录与 AI 目录版本。现有库存、包装、出入库流水、图片、原货号、供应商资料、分类、仓库等业务数据不能变化。
- 现有生产 AI 镜像 2414 条（实际数量以冻结快照为准），和业务库约 109 条的差异是已知正常事实。只对镜像已有且同 `product_id` 的记录更新 `product_code`；不凭空补录、不重新生成向量、不调用模型、不重建索引或重置每日费用账本。
- AI 原始同步 `manifests` 在生产环境已确认为零文件，不得依赖它、伪造它或将它作为切换前提。旧目录的 `catalog_fingerprint` 表示原始同步事实，不要伪称其为变更后的快照指纹。另加独立的 `catalog_revision` 标识编号切换，旧 AI 页面 / 反馈 / 复制结果必须失效；确保以后正常 AI 同步仍工作。
- 不换 MySQL、不重构前后端架构、不改 UI 视觉、不新建后台服务、不添加付费能力。

## 上次失败的工程原因与禁止事项

1. **没有先读懂生产数据。** 合成 CI 数据中有 manifest，生产没有；停机后才发现。新方案必须有不写入数据的 preflight，验证真实 schema、AI 元数据、索引、两个 lock、文件权限、镜像和业务货号的相容性，列出异常，不自动修正。
2. **停机期间调试迁移脚本。** 新方案必须先在隔离的、与生产结构一致的备份副本上完整执行 `preflight -> migrate -> plan -> execute -> verify -> restore rehearsal`，不许在停机期间现场开发。
3. **发布文件版本不明。** 旧版和新版 backend.zip 混淆；误将 GitHub Artifact 的 digest 当成本地下载 ZIP SHA。新发布必须一个不可变 release 包，含 commit、构建时间、文件实际 SHA256 和唯一 release ID；部署使用经过演练的**同一个脚本**，明确失败出口。不得生产 curl raw GitHub。
4. **过度检查与反复续步骤。** 所有可以预判的检查前移，阶段止损条件一次定义。线上只允许已经演练过的、完整封装的动作；失败即维持/恢复原业务，不在服务器临时补写代码。
5. **错误权限修复风险。** AI catalog 目录和 SQLite 文件在当时是 `root:inventory`、inventory 只读；旧工具用 inventory 写必失败。预检应确定实际执行身份及所需的最小权限，不允许 `chmod -R` 或 `chown -R`。
6. **测试与上线概念混淆。** 单元测试、CI、真实副本演练、发布包校验、生产人工验收是不同门槛，任何一项不能替代其他项。

## 模块设计

1. **read-only preflight**：在现有原版 SQLite schema 上工作，不依赖新 Alembic revision。输出机器可读 JSON 和清晰中文汇总，零写入、零 AI 调用。识别 catalog 与业务商品 ID 集合、旧号错配清单、非空/异常/重复号、索引 source identity、SQLite journal、运行任务和权限。不要求不存在的 manifest。不打印凭据。
2. **normal numbering**：新商品发号代码与独立 Alembic 迁移；事务内顺序发号，候选号冲突/回滚/同时写入/跨月/导入/停用/无分类都覆盖；严格按北京时区。
3. **offline cutover**：先固化映射和非编号字段快照摘要；执行前对照审核过的快照，冻结所有写入。SQLite 同一主库 + ATTACH 的跨库事务，要求非 WAL + 正确 journal 设置与支持的路径条件；不能不经论证改成两个独立提交。对 target code 重叠使用临时唯一值再改最终编号。迁移状态须防重复执行并区分“提交成功但报告写入失败”。
4. **verify and recovery**：全量检查映射、每商品/仓库箱数、所有其他表摘要、外键和完整性；AI 仅更新编号与目录变更元数据，向量、预算、图片文件哈希不变。提交前失败测试 rollback，提交后失败测试 verify-only。提供严格成套恢复程序；恢复需考虑真实业务写入后不能覆盖新数据。

### 本阶段补齐

- 业务库旧 Alembic 版本和所需旧字段；旧自家编号的空值、空白、重复、异常格式统计。样例只输出至多 20 个商品 ID，不打印完整商品记录。重复/空旧号须按商品 ID 审查映射，不自动修复，也不填入供应商原货号。
- 镜像来源、文档身份和元数据类型/原始同步指纹；镜像外 ID 为阻塞，旧号漂移为警告。镜像小于业务库与零 manifest 不阻塞，不创建 manifest。
- 原版 vs02 的必要索引表/字段、source binding、上下文来源、模型和 namespace 对应 index_key，以及原始同步指纹一致性。没有生成向量、修改索引或虚构新的目录版本。
- 预算库存在、只读可读、`user_version=1` 及两张账本表的必要字段；不初始化预算库，不改费用记录。
- 两个现有调用锁、业务库父目录、AI 根/镜像/索引目录和关键文件的类型、属主、权限及当前进程访问能力；生产执行用户/附加组、ACL、父目录遍历和日志创建权限保留 `PENDING`。副本权限、Windows 模式位和 `os.access` 都不能证明生产授权；存在锁文件也不证明锁已释放。
- 四个数据库均在打开前拒绝 `-wal`、`-shm` 或 `-journal`。即使没有 sidecar，WAL 文件头也会阻止连接；不会 checkpoint、恢复或删除 sidecar。正常读取使用 `mode=ro`、`query_only`，连接显式关闭。
- JSON 输出在 stdout，简短中文结果在 stderr。读取到的关键文件报告执行前后 SHA256；变化即阻塞。仅比较哈希不证明备份历史时点、来源或跨库一致性。
